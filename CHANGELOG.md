# Changelog

## Unreleased

- Freshness: the fresh workflow says every week which signed index is current (fresh.json, naming main's index.json by its sha256 and the date it stays current until, signed into fresh.sig by a key of its own that can say nothing else, on the branch fresh), so an AerieOS that ships that key can tell an index a mirror keeps answering after it was replaced. tools/catalog-sign.py keygen --fresh makes the key, fresh writes the statement, and tools/test_check.py holds it
- Held downloads: every pack is at pack format 5 and every entry says what its downloads are held to (held: pinned, or installer with the installer's own sentence), every Docker app names its images by digest, and Gemini's program is a declared download. The check reads each entry as an install does, refuses an open one, and takes nothing away from a listed release: an entry that moves to a newer pack format keeps its older pin (older). The releases before the first that reads pack format 5 are off aerieos-releases, and tools/aerieos-release.py lists that one once it is out
- Moving a pin: a scheduled job (.github/workflows/pins.yml) asks each pack how its entry says a newer pin is found and proposes what moved as a pull request, which a maintainer reviews and the sign workflow publishes
- Signing: the index is stamped with the moment it is signed (generated, forward only, nothing else of the file touched), so two signed indexes never carry one date and an install can refuse the older; the sign workflow runs from main for a named branch with main's own copies of the tools and no fallback to the branch's (a main that lacks them signs nothing), names every action by its full commit, installs its one library pinned with hashes into the runner's own python, reads the entries in one job that holds no secret, installs a third party's pack in another, and signs, under the environment sign, the very commit those two answered for; the check tells an AerieOS that asks for it that an official entry is one (the entry's own tier, held to this repository's folders), where it read the word from the manifest. tools/test_sign.py holds the stamp and the word
- What an install downloads: the check installs a third party's changed pack on its own runner with the installer of each AerieOS release it serves, driven from a checkout (tools/offline-install.py): that release's own code fetches the pack at its pin, holds each download its manifest declares to its sha256 or its publisher's signature, cuts the network and runs the steps, so a pack that fetches anything else fails before a maintainer reads it. No step keeps a way to root (no_new_privs, by the driver or by the release's bb-netcut), and the installs run in a job apart from the one that reads the entries. tools/test_offline.py holds it, and the check workflow fails if its runner cannot cut the network for a step
- Whose an entry is: the check says whose each changed entry is, on a pull request, on a push to main and before the index is signed, and refuses a change that crosses owners: Aerie's own entries and a third party's in one change, two owners' entries in one change, a third party's entry removed, handed to another owner, changed with no new pin beyond withdrawn and tier, or moved beside any other file here. A pull request is held to it by main's copy of the workflow and the tools, which it cannot change (.github/workflows/whose.yml, on pull_request_target, the pull request read as data). From a fork, an entry is moved only by the account its repository is under, files are added only in a new entry's new folder, and a pin is taken only where its commit is on a branch or a tag of the repository the entry names. tools/test_whose.py, tools/test_reach.py and tools/test_workflows.py hold the rules; .github/CODEOWNERS names the maintainers for the signature, the key, the tools, the workflows and Aerie's own packs
- The vetting check: tools/catalog-check.py fetches an entry at its pin, checks the commit and its archive's sha256, and holds its manifest (a pack's bbtool.json, an app's bbapp.json and compose.yml) to BuilderBot's own validators, the entry's name and platforms to the manifest's, and an official entry to this repository's own packs; CI runs it on a pull request's changed entries and, with the signature, on every push to main (R169 step 3)
- A Docker app in the catalog, whoami (traefik/whoami, MIT) under packs/apps/whoami, an index entry of kind app naming its folder (R170 step 7)
- The shipped toolchains and coding agents as packs under packs/official and packs/agents, each pinned in the index at tier official with its folder as path (R170 step 6)

### Added

- The signed index: index.json pinning each pack to an exact commit and its archive's sha256, index.sig by the maintainers' Ed25519 key whose public half ships with BuilderBot, and tools/catalog-sign.py to make a key, sign and verify.
